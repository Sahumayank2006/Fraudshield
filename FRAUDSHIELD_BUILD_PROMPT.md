## 1. PRODUCT IN ONE PARAGRAPH

FraudShield watches a stream of payment transactions. Each transaction gets a calibrated fraud probability from a hybrid model (Isolation Forest + autoencoder anomaly scores fused into a class-weighted XGBoost, then probability-calibrated). A cost-based two-threshold policy converts probability into **APPROVE / REVIEW (step-up) / BLOCK**. Every flagged transaction comes with SHAP reason codes in plain English. Analysts work a case queue, confirm or dismiss, and their feedback is stored. A drift monitor tracks PSI per feature and score distribution. A "Threshold Lab" lets the audience move the threshold and watch precision, recall and money lost change live. A scripted **Attack Simulation** injects a fraud burst into the live stream so the audience sees detection happen in real time.

## 3. DATA

### 3.1 Primary: "LedgerSim" synthetic bank simulator (`src/simulator.py`)

Build a realistic, seedable generator. It must produce a time-ordered transaction table with **account-level history**, so velocity and behavioural features are meaningful (ULB has no account IDs).

Entities: ~20,000 accounts, ~1,500 merchants across ~12 merchant categories, devices, IPs/regions. Default size 400,000 transactions across 60 simulated days (configurable; `--fast` uses 120,000 over 30 days). Overall fraud rate about 0.5 to 0.8% (configurable, so there are enough positives, around 2,000+, for stable estimates).

Legitimate behaviour: each account has its own spending profile (typical amount lognormal, preferred categories, usual hours, home region, usual devices), weekly and daily seasonality, salary-day bumps, occasional legitimate oddities (a large one-off purchase, travel) so anomaly detectors produce realistic false positives.

Fraud typologies (label each transaction with a `fraud_type` column for analysis, hidden from models):
1. **Card testing**: bursts of tiny amounts at new merchants in minutes, then one large purchase.
2. **Card-not-present**: new device, new region, unusual category, amount spike.
3. **Account takeover (ATO)**: new device + IP, password-reset event flag, then fast full-balance drain transfer.
4. **Mule / cash-out chain**: new account receives several in-flows then immediately cashes out most of it; short dwell time.
5. **Authorised push payment (APP)**: first-time payee, large amount, odd hour, customer session long.

**Concept drift is mandatory**: in the last ~25% of the timeline, introduce a new typology variant (e.g. fraud shifts to lower amounts, daytime hours, and a new merchant category) and change fraud mix proportions. This is what makes the anomaly branch and the drift monitor demonstrably useful. Also include **label delay**: fraud labels are only "mature" 7 days after the transaction; the evaluation code must respect a label-maturity window.

Columns (minimum): `txn_id, ts, account_id, merchant_id, merchant_category, amount, channel (card_present/online/upi/transfer), device_id, device_is_new, ip_region, region_mismatch, hour, is_night, oldbalance, newbalance, dest_account_id, dest_is_new_payee, session_seconds, pwd_reset_last_24h, is_fraud, fraud_type`.

## 5. ML SPECIFICATION

### 5.1 Split and protocol
- Sort by time. Split 70 / 15 / 15 into train / validation / test **by timestamp, never shuffled**. The drift segment falls mostly in validation and test, on purpose.
- All fitting (scalers, encoders, imputers, SMOTE, anomaly models) on training data only. Use `imblearn.pipeline.Pipeline` where resampling is used.
- Model selection by expanding-window time-series CV inside training, scored by PR-AUC (average precision).
- Test set touched once, at the very end. Bootstrap 95% CI (1,000 resamples) on every reported test metric.
- Cost constants in `config.py`: `C_FN` defaults to a per-transaction **amount-based** loss (lost amount plus a fixed handling fee), `C_FP` fixed (e.g. 5 currency units of analyst time and friction). Support both a flat-ratio (100:1) and an amount-weighted cost; the UI lets the user switch.

### 5.2 Features (`features.py`) — one code path for training and serving
All rolling features use **strictly past** data relative to each transaction (strict `<` timestamp). Write a unit test that proves no future leakage (shuffle future rows, features of earlier rows must not change).
- Amount: `log_amount`, `amount_zscore_by_account` (expanding mean/std, past only), `amount_to_balance_ratio`, `drains_account`.
- Time: `hour`, `is_night`, `time_since_last_txn`, `time_since_account_open`.
- Velocity: `txn_count_1h/24h/7d`, `amount_sum_1h/24h`, `distinct_merchants_24h`, `distinct_devices_7d`, `new_merchant_flag`, `new_payee_flag`.
- Behavioural deviation: category rarity for the account, region mismatch, device novelty, session anomaly.
- Balance (PaySim and LedgerSim): `errorBalanceOrig`, `errorBalanceDest`.
- Entity-level online state: serving keeps a per-account rolling state in memory (deque + dict) so single-transaction scoring computes the same features as training. Provide `FeatureStore` with `update(txn)` and `features_for(txn)`.
- Anomaly features: `iso_score`, `ae_error` (see 5.4).

### 5.3 Supervised models and experiment matrix
Implement and run **all ten** experiments, logging every result to `artifacts/experiments.json` with CI:

| ID | Model | Imbalance strategy | Purpose |
|----|-------|--------------------|---------|
| E1 | Logistic Regression | none | floor, cost of ignoring imbalance |
| E2 | Logistic Regression | class weights | weighted baseline |
| E3 | Random Forest | balanced_subsample | bagging baseline |
| E4 | XGBoost | scale_pos_weight | primary supervised model |
| E5 | XGBoost | SMOTE (sampling_strategy 0.2) in CV | ablation: does resampling help? |
| E6 | LightGBM | class weights | speed/accuracy comparison |
| E7 | Isolation Forest | unsupervised | label-free baseline |
| E8 | Autoencoder | unsupervised | reconstruction-error baseline |
| E9 | XGBoost + anomaly scores | class weights | hybrid (proposed) |
| E10 | Stacked ensemble (LR meta-learner on out-of-fold base scores) + calibration | class weights | best-of-breed candidate |

Report per experiment on validation AND test: PR-AUC, ROC-AUC (for contrast), recall at precision 0.80 and 0.90, F2, MCC, expected cost at its own cost-optimal threshold, Brier score, training time, inference latency per row (median, p95). Also report a **test-period split into early and late halves** so drift impact on each model is visible (H2: hybrid helps most in the late period).

Tuning: Optuna, 25 trials for XGBoost (10 in `--fast`), objective validation PR-AUC. Early stopping on `aucpr`.

### 5.4 Hybrid fusion (the headline contribution)
1. Fit Isolation Forest (300 trees) and the autoencoder on **legitimate training rows only** (scaled with train statistics). Autoencoder architecture mirrors the report: `d-16-8-4-8-16-d`, ReLU, Adam 1e-3, early stopping, ~50 epochs max.
2. For **training rows**, generate **out-of-fold** anomaly scores (K=5 time-aware folds); for validation/test/serving use the full-train models. Document why in code comments.
3. Append `iso_score` and `ae_error` to the feature matrix, train class-weighted XGBoost, then **calibrate** (isotonic on the validation set; also fit Platt and choose the lower Brier score). Save the reliability diagram data.

### 5.5 Decision policy (`policy.py`)
- `t2` (BLOCK): lowest threshold where validation precision >= 0.90.
- `t1` (REVIEW): cost-optimal threshold on validation, **capped so the review queue does not exceed analyst capacity** (config: reviews per 1,000 transactions, default 6). Guarantee `t1 < t2`.
- Thresholds written to `artifacts/thresholds.json`, never hard-coded. The API reads them at startup and supports live override from the Threshold Lab (session-scoped, clearly flagged as "what-if", not persisted).
- Return a decision: `APPROVE | REVIEW | BLOCK` plus `fraud_probability`, `anomaly_score`, `model_version`, `top_reasons`, `latency_ms`.

### 5.6 Explainability (`explain.py`)
- Global: mean |SHAP| ranking, beeswarm-style data (feature value vs SHAP, sampled to 2,000 rows), dependence data for the top 6 features. Write them as JSON for the frontend to draw itself.
- Local: per-transaction contributions. Prefer XGBoost's native `predict(..., pred_contribs=True)` (exact TreeSHAP, no extra dependency); use the `shap` package only if it is installed and needed for the global plots.
- **Reason codes**: map the top 3 positive contributors to plain-English strings via a dictionary in `explain.py` (e.g. "Amount is 14x higher than this account's usual", "Payment from a device never seen on this account", "Funds sent within minutes of a password reset", "Third transaction to a new merchant in 4 minutes"). Reasons must be generated from real feature values, with the actual numbers filled in.
- Add a permutation-importance cross-check on validation.
- Add a visible caution in the UI: explanations describe the model, not causality.

### 5.7 Monitoring (`monitor.py`)
- PSI per feature (reference = training period, current = rolling recent window), bins by reference quantiles, clip epsilon. Status bands: below 0.10 stable, 0.10 to 0.25 moderate, above 0.25 major.
- Score distribution drift (PSI on the score), weekly precision/recall as labels mature (respect the 7-day label-maturity window), and a trigger rule: PSI > 0.25 on the score or a drop in recall at fixed precision creates a "Retrain recommended" alert.
- Implement a real **challenger retrain**: `POST /api/retrain` retrains on all data up to "now" in the replay (fast config), evaluates challenger vs champion on the latest mature window, and only promotes if it passes the same gate. Show both models side by side. Keep the previous model for one-click rollback.

### 5.8 Fairness and robustness section (small but real)
- Compute false-positive rate by segment (region, channel, account-age bucket) and show it in a "Fairness audit" panel with a plain-language note about proxy features.
- Robustness probe: evaluate on a copy of the test set where fraud amounts are shrunk by 30% (evasion simulation) and show how recall changes per model.
